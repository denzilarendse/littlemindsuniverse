# Teacher evidence orphan reconciliation: design and safety contract

## Status

This is a report-only inventory, not an automatic deletion mechanism. It identifies old objects in the dedicated private teacher-evidence quarantine bucket that have no matching metadata row in public.teacher_chat_evidence. It does not delete, move, or modify any object.

## Why report-only

The client uploads a private object and then registers its metadata. If registration and compensating removal both fail, the object can be left behind. However, an object without metadata is not proof that it is disposable: a legitimate upload may have been interrupted by an outage or may be awaiting manual recovery. Automatic deletion based only on absence of metadata would violate the no-data-loss requirement.

## Candidate rules

The service-role-only RPC lists a candidate only when all conditions hold:

1. It belongs to teacher-chat-evidence-quarantine, never another bucket.
2. Its path matches the exact four-segment UUID-based teacher/classroom/learner/file format generated by the upload UI and uses an allowed extension.
3. It is older than the requested minimum age. The RPC rejects thresholds shorter than 24 hours or longer than 365 days. Operators should start with at least seven days.
4. No metadata row exists for the exact storage path. Even a row marked deleted protects the object from orphan classification; the established retention workflow owns those objects.
5. The result limit is between 1 and 100. There is no delete operation, scheduler, or client-facing execute grant.

## Operator workflow

1. Apply the migration only in an isolated Supabase staging project.
2. Call the RPC with service-role credentials from a controlled operator context. Start with a seven-day threshold and a small limit.
3. Review candidate IDs, path shape, and timestamps against upload/error logs and any recoverable teacher report. Do not expose full object paths or learner identifiers in general application logs.
4. Re-run the inventory after a delay to confirm the object remains unregistered.
5. Recover/register a legitimate file only when ownership and class authorization can be verified. If the file cannot be confidently classified, leave it untouched and escalate for authorized manual review.
6. Any future deletion capability requires a separate reviewed change with a dry-run report, explicit approval record, a second check immediately before deletion, idempotent bounded deletes, an audit trail, and staging fault-injection tests. This RPC alone must never be treated as authorization to delete.

## Tests and limitations

The new source-contract test checks bucket scoping, path shape, minimum age, bounded result count, service-role-only access, metadata protection, and absence of destructive operations. These are static tests. They do not substitute for executing the SQL against a staging database, validating the real storage.objects metadata shape, or exercising RLS and concurrent uploads.

No production migration, storage object, policy, scheduler, or database row is changed by this branch.
